## 1. Connection Lifecycle & Wire Protocol

### 1.1 Endpoint & Query Authentication
- **Endpoint**: `ws://<backend_host>:<port>/ws` (configured via `NEXT_PUBLIC_WS_URL`)
- **Connection Handshake**:
  - Staff clients connect with a query parameter or authentication header:
    ```text
    GET /ws?token=<jwt_access_token> HTTP/1.1
    Host: api.yourdomain.com
    Upgrade: websocket
    Connection: Upgrade
    Sec-WebSocket-Key: ...
    Sec-WebSocket-Version: 13
    ```
  - Public guest QR clients connect without a staff token:
    ```text
    GET /ws?qrToken=<session_or_table_token> HTTP/1.1
    ```
- **Connection States**:
  `CONNECTING` -> `CONNECTED` -> `DISCONNECTED` -> `RECONNECTING` -> `ERROR`

### 1.2 Wire Frame Envelope
Every frame exchanged over the socket adheres to this standard envelope:

```json
{
  "id": "msg_9b1a8d02-e25f-4a31-8bc8-6019c00b2123",
  "type": "ORDER_CREATED",
  "topic": "orders:all",
  "payload": { ... },
  "timestamp": "2026-10-10T15:30:00.000Z"
}
```

- `id`: Unique UUID v4 generated by the sender for deduplication.
- `type`: High-level event identifier.
- `topic`: Channel/room namespace (e.g., `orders:all`, `order:ord-101`, `kitchen:kots`, `billing:all`).
- `payload`: Typed event payload.
- `timestamp`: ISO 8601 UTC timestamp.

### 1.3 Heartbeat & Liveness (Ping/Pong)
- To prevent reverse proxy timeouts (e.g. Nginx 60s idle drop), either client or server can emit a lightweight heartbeat every 30 seconds:
  ```json
  {
    "type": "HEARTBEAT",
    "timestamp": "2026-10-10T15:30:30.000Z"
  }
  ```

## 2. Topic Subscription & Channel Authorization

### 2.1 Subscription Protocol
Upon establishing a connection, the client subscribes to relevant topics based on station role:

```json
{
  "action": "SUBSCRIBE",
  "topic": "kitchen:kots",
  "token": "eyJhbGciOiJIUzI1NiIsIn..."
}
```

### 2.2 Unsubscription Protocol
```json
{
  "action": "UNSUBSCRIBE",
  "topic": "kitchen:kots"
}
```

### 2.3 Channel Authorization Matrix

| Channel / Topic | Purpose | Permitted Roles / Audience | Scope |
|---|---|---|---|
| `orders:all` | Stream of all order changes | `ADMIN`, `MANAGER`, `WAITER`, `CASHIER` | Tenant / Outlet |
| `order:{orderId}` | Updates for a specific order | Guest of that order, Staff | Order ID |
| `kitchen:kots` | Active KOT dispatch & status | `KITCHEN_STAFF`, `MANAGER`, `ADMIN` | Kitchen Stations |
| `billing:all` | Bill generation & settlements | `CASHIER`, `MANAGER`, `ADMIN` | Billing Desks |
| `inventory:alerts` | Low stock and item 86 alerts | `ADMIN`, `MANAGER`, `KITCHEN_STAFF` | Inventory Ops |
| `printers:all` | Hardware status & spool alerts | `ADMIN`, `MANAGER` | Hardware Fleet |

> [!CAUTION]
> The backend server MUST reject unauthorized subscription attempts. A customer scanning Table 01 must NEVER be permitted to subscribe to `billing:all`, `kitchen:kots`, or `order:ord-999` belonging to another table.

## 3. Comprehensive Event Catalog

### 3.1 `order.created` (`ORDER_CREATED`)
- **Direction**: Server -> Client
- **Purpose**: Broadcast new customer or POS order to waiter staff and managers.
- **Required Role**: `WAITER`, `MANAGER`, `ADMIN`
- **Scope**: Tenant / Outlet (`orders:all`)
- **Recoverable**: Yes (Available via `GET /api/v1/orders`).
- **Sample Payload**:
  ```json
  {
    "orderId": "ord-2026-1042",
    "orderNumber": "ORD-1042",
    "status": "PLACED",
    "order": {
      "id": "ord-2026-1042",
      "orderNumber": "ORD-1042",
      "qrContext": { "type": "TABLE", "identifier": "Table 04", "tableId": "tbl-04" },
      "status": "PLACED",
      "source": "CUSTOMER_QR",
      "paymentPreference": "PAY_LATER",
      "grandTotal": 1420.00,
      "items": [
        { "name": "Butter Chicken", "quantity": 2, "totalPrice": 880.00 },
        { "name": "Garlic Naan", "quantity": 4, "totalPrice": 240.00 }
      ]
    }
  }
  ```

### 3.2 `order.status.updated` (`ORDER_UPDATED`)
- **Direction**: Server -> Client
- **Purpose**: Notify guest mobile device and staff UI of order progression (`CONFIRMED`, `PREPARING`, `READY`, `SERVED`, `CANCELLED`).
- **Required Role**: Public Guest (on `order:{orderId}`), Staff (on `orders:all`)
- **Scope**: Order or Tenant
- **Sample Payload**:
  ```json
  {
    "orderId": "ord-2026-1042",
    "orderNumber": "ORD-1042",
    "status": "PREPARING",
    "note": "Chef started cooking on Grill Station 1"
  }
  ```

### 3.3 `kot.created` (`KOT_CREATED`)
- **Direction**: Server -> Client
- **Purpose**: Alert kitchen KDS screens that a new ticket has arrived.
- **Required Role**: `KITCHEN_STAFF`, `MANAGER`, `ADMIN`
- **Scope**: Kitchen Station (`kitchen:kots`)
- **Sample Payload**:
  ```json
  {
    "kotId": "kot-2026-0819",
    "kotNumber": "KOT-0819",
    "status": "NEW",
    "kot": {
      "id": "kot-2026-0819",
      "kotNumber": "KOT-0819",
      "orderId": "ord-2026-1042",
      "orderNumber": "ORD-1042",
      "qrContext": { "type": "TABLE", "identifier": "Table 04" },
      "urgency": "NORMAL",
      "items": [
        { "name": "Butter Chicken", "quantity": 2, "status": "PENDING" }
      ],
      "createdAt": "2026-10-10T15:32:00.000Z"
    }
  }
  ```

### 3.4 `kot.status.updated` (`KOT_UPDATED`)
- **Direction**: Server -> Client
- **Purpose**: Realtime sync between KDS stations when chef marks ticket `ACCEPTED`, `PREPARING`, `READY`, or `SERVED`.
- **Required Role**: `KITCHEN_STAFF`, `WAITER`, `MANAGER`
- **Scope**: `kitchen:kots`
- **Sample Payload**:
  ```json
  {
    "kotId": "kot-2026-0819",
    "kotNumber": "KOT-0819",
    "status": "READY",
    "preparedAt": "2026-10-10T15:45:00.000Z"
  }
  ```

### 3.5 `bill.created` (`BILL_UPDATED`)
- **Direction**: Server -> Client
- **Purpose**: Notify cashier desk and table of bill generation or tax calculation changes.
- **Required Role**: `CASHIER`, `MANAGER`, Guest of Order
- **Scope**: `billing:all`, `order:{orderId}`
- **Sample Payload**:
  ```json
  {
    "billId": "bill-2026-0419",
    "bill": {
      "id": "bill-2026-0419",
      "billNumber": "INV-2026-0419",
      "orderId": "ord-2026-1042",
      "status": "ISSUED",
      "subtotal": 1420.00,
      "totalTax": 71.00,
      "grandTotal": 1491.00,
      "dueAmount": 1491.00
    }
  }
  ```

### 3.6 `payment.status.updated` (`PAYMENT_UPDATED`)
- **Direction**: Server -> Client
- **Purpose**: Instant notification of UPI / Card / Cash settlement or refund event.
- **Required Role**: `CASHIER`, `MANAGER`, Guest of Order
- **Scope**: `billing:all`, `order:{orderId}`
- **Sample Payload**:
  ```json
  {
    "paymentId": "pay-2026-9021",
    "billId": "bill-2026-0419",
    "amount": 1491.00,
    "method": "UPI",
    "status": "SUCCESS",
    "transactionReference": "UPI-REF-981240182",
    "remainingDueAmount": 0.00
  }
  ```

### 3.7 `inventory.stock.updated` (`INVENTORY_STOCK_UPDATED`)
- **Direction**: Server -> Client
- **Purpose**: Realtime sync when stock changes, alert when item drops below threshold, or automatic item 86 broadcast.
- **Required Role**: `ADMIN`, `MANAGER`, `KITCHEN_STAFF`
- **Scope**: `inventory:alerts`
- **Sample Payload**:
  ```json
  {
    "itemId": "inv-041",
    "name": "Paneer (Fresh Cottage Cheese)",
    "currentStock": 1.5,
    "unit": "KG",
    "isLowStock": true,
    "auto86edMenuItems": ["item-paneer-butter-masala"]
  }
  ```

### 3.8 `print_job.status.updated` (`PRINT_JOB_UPDATED`)
- **Direction**: Server -> Client
- **Purpose**: Notify admin or cashier of hardware spool status (`COMPLETED`, `FAILED`, `OFFLINE`).
- **Required Role**: `ADMIN`, `CASHIER`, `MANAGER`
- **Scope**: `printers:all`
- **Sample Payload**:
  ```json
  {
    "jobId": "job-1092",
    "printerId": "prn-01",
    "printerName": "Kitchen Station 1",
    "status": "FAILED",
    "errorMessage": "Hardware out of paper (cutter open)"
  }
  ```

## 4. Reconnection, Deduplication & Fallback Strategy

### 4.1 Client Reconnection with Exponential Backoff
The frontend WebSocket client (`WebSocketManager` in `src/services/websocket/socket.service.ts`):
1. Detects abnormal closure (`onclose` without explicit user signout).
2. Sets state to `RECONNECTING`.
3. Reconnects with exponential backoff:
   - Initial delay: 1,000 ms
   - Backoff factor: 1.5x
   - Max delay: 30,000 ms
   - Max attempts: 10
4. Upon successful reconnect:
   - Resets attempt counter.
   - Re-subscribes to all active topics.
   - Refetches latest state via HTTP API to reconcile any missed events during downtime.

### 4.2 Message Deduplication
Every frame has a unique `id` (UUID). The frontend tracks the last 500 processed message IDs. If an identical message ID is received within 60 seconds (due to network retries or cluster republishing), it is discarded without duplicate UI triggers.

### 4.3 Fallback to Polling if WebSockets Unavailable
If corporate firewalls, captive portals, or mobile browser networks block WebSocket connections:
- The frontend falls back to standard HTTP polling:
  - Active Orders: Polls `GET /api/v1/orders` every 15 seconds.
  - Kitchen KDS: Polls `GET /api/v1/kitchen/kots` every 10 seconds.
  - Bill Settlement: Polls `GET /api/v1/bills/:id` every 5 seconds while on payment screen.

## 5. Backend Transactional Outbox Pattern (Phase 3B.3)

To ensure reliable, at-least-once event delivery and prevent dual-write anomalies (e.g., database commit succeeding but socket emit failing):

### 5.1 Outbox Schema (`outbox_events` table)
Every mutating operation that triggers a business event persists an outbox record inside the same PostgreSQL transaction snapshot (`$transaction`):
- `id`: UUID (Primary Key)
- `tenant_id`: UUID
- `event_type`: VARCHAR(100) (e.g. `order.created`, `kot.created`)
- `topic`: VARCHAR(100) (e.g. `orders:all`, `kitchen:kots`)
- `payload`: JSONB
- `status`: ENUM (`PENDING`, `PROCESSING`, `PUBLISHED`, `FAILED`)
- `retry_count`: INT (default 0)
- `last_error`: TEXT (captures transport failure details)
- `published_at`: TIMESTAMPTZ(6)
- `created_at` / `updated_at`: TIMESTAMPTZ(6)

### 5.2 Decoupled Event Dispatch Lifecycle
1. **Commit**: Order and KOT records commit along with the `PENDING` outbox event in PostgreSQL.
2. **Asynchronous Dispatch**: The background outbox worker (`outboxService.dispatchEvent`) fires non-blocking HTTP post-commit triggers.
3. **Transport Resilience**: If the WebSocket transport or broker drops, the business order remains safely committed in PostgreSQL; the outbox record increments its retry counter and records the error for asynchronous replay.
4. **Transport Bridge**: The pending `@fastify/websocket` transport daemon (Phase 3B.4) will sweep `outbox_events` with `status = PENDING` and broadcast frames to connected clients according to the subscription topic matrix.
